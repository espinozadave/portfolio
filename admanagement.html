Active Directory Administration & SIEM Event Analysis

🔧 This is an active lab project, updated as new phases are completed. Currently working on: assigning and testing access-control permissions across department groups.

Overview

This project focused on deploying an on-premises Active Directory environment using a Windows Server Domain Controller and a domain-joined Windows client, then integrating both systems with a Wazuh SIEM to monitor and interpret identity-related security events. The goal was to gain hands-on experience administering core Active Directory functions, including organizational units, user accounts, security groups, and permissions, while building the SIEM analysis skills needed to correlate administrative actions with their corresponding Windows security events. This project reflects a core responsibility found in many IT support and security analyst roles: managing identity infrastructure and maintaining visibility into changes made within it.

The lab consists of three systems communicating with each other within an isolated internal network:

  • Windows Server – Domain Controller (192.168.10.23)
  • Ubuntu – Wazuh Server (192.168.10.3)
  • Windows – Wazuh Agent (192.168.10.24)

Objective

  • Gain hands-on experience deploying and administering an Active Directory environment, including creating and managing organizational units, user accounts, security groups, and permissions
  • Understand how identity and access management actions are recorded within Windows security logs
  • Practice reading, interpreting, and correlating Active Directory events within a SIEM platform (Wazuh) to build practical security monitoring and log analysis skills
  • Reinforce the relationship between administrative actions and their corresponding audit trail, a core concept in identity security and incident detection

Tools & Technologies Used

  • Windows Server 2022 (Domain Controller)
  • Windows 10 (domain-joined client)
  • Wazuh (SIEM manager on Ubuntu, agents on DC + client)
  • VirtualBox (Internal Network)
  • Active Directory Users and Computers, Advanced Audit Policy Configuration

Lessons Learned (So Far..)

SIEM visibility depends on agent coverage, not network proximity:

  • One of my early assumptions was that being on the same network as the Wazuh manager meant activity would be visible. That's not how it works only machines running an installed Wazuh agent generate telemetry, and events are logged on whichever machine the action actually occurred on. This reshaped how I think about SIEM deployment: visibility is a deliberate design choice, not a byproduct of network topology.
Small environment quirks can cost the most time:
  • A Server Core vs. Desktop Experience mismatch during initial install, a Guest Additions/display issue, and a firewall rule silently blocking ICMP all turned into real troubleshooting exercises. None of these were "hard" problems conceptually, but they were good reminders that a lab environment surfaces the same kind of small, annoying issues that show up in production and that methodical troubleshooting (checking one variable at a time: network adapter, firewall rule, service state) matters more than knowing the "big" concepts.
Temporary changes need a deliberate rollback step:
  • Getting internet access to the DC for the Wazuh agent install meant temporarily adding a NAT adapter but leaving that in place afterward would have quietly widened the attack surface of a domain controller for no ongoing reason. Disabling it once the agent was confirmed working reinforced a habit I want to carry forward: every temporary change needs a planned reversal, not just a mental note.
Audit policy has to be turned on deliberately — logging isn't automatic:
  • Enabling Advanced Audit Policy (Account Management and DS Access, Success events) via GPO made it clear that Windows doesn't log detailed AD changes out of the box. If I want to actually observe and correlate access-control events later, the audit policy has to be configured before the activity happens, not after.

Next Steps

  • Assign NTFS permissions to department security groups on shared department folders, so each group (IT, Security, HR, Finance) has access only to its own resources
  • Enable object access auditing (SACLs) on those shared folders to capture access attempts — including denied access — in the Security event log
  • Validate end-to-end visibility in Wazuh, confirming that permission changes and access attempts on the DC are correctly forwarded and searchable in the SIEM
  • Test cross-department access attempts (e.g., a Finance user attempting to open the HR share) to generate and analyze real access-control violation events
  • Explore delegated AD permissions (e.g., allowing the IT group limited rights to reset passwords within their OU) as a follow-up phase, to test more advanced DS Access auditing scenarios
  • Continue documenting each phase with screenshots and captions as the project progresses, since this is being built and published as an active, in-progress lab rather than a finished writeup
